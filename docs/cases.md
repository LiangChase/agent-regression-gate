# Case Format and Deterministic Rules

Cases are YAML or JSON files loaded and validated before the SUT is started. The initial airline dataset is [`cases/airline/cases.yaml`](../cases/airline/cases.yaml). Each case has a stable `id`, `version`, `risk_level`, tags, optional precondition notes, one or more user turns, timeout, and evaluator rules. Each rule has its own stable ID and severity. A `parameters` list expands one case definition into distinct concrete instances; `{{ variable }}` placeholders are substituted in turn text and rule parameters, and reports retain the base case ID and concrete values. Preconditions currently document assumptions only; the SUT adapter does not offer context seeding.

```yaml
id: AIR-01
version: "1"
name: Flight status uses the requested flight
risk_level: critical
tags: [flight-status]
turns:
  - What is the status of flight FLT-123?
rules:
  - id: AIR-01-R1
    type: tool_args_match
    severity: critical
    params:
      tool: flight_status_tool
      equals:
        flight_number: FLT-123
```

| Type | Parameters | Meaning |
|---|---|---|
| `tool_must_be_called` | `tool` | At least one matching call exists |
| `tool_never_called` | `tool` | No matching call exists |
| `tool_call_count` | `tool`, optional `min`/`max` | Matching call count is within bounds |
| `tool_args_match` | `tool`, one or more of `equals`, `required_fields`, `matches` | Every matching call satisfies argument constraints; nested paths use dots |
| `tool_order` | `tools` | Listed calls occur in order (subsequence); unrelated calls may appear before, between, or after them |
| `tool_allowlisted` | none | Every observed business tool call is listed for its calling agent |
| `handoff_required` | optional `target` | A handoff exists, optionally to a matching target |
| `final_response_contains` / `final_response_not_contains` | `text` string or list | Case-insensitive constraint on the last recorded assistant message; a list requires every item for `contains` and none for `not_contains` |
| `trace_complete` | optional `require_tool_trace` | Collection is complete and required tool evidence exists |
| `final_state` | `equals` object | Final SUT context matches expected values |

`gate validate-cases` checks parsing, required fields, duplicate concrete case/rule IDs, unknown fields/evaluator types, parameter shapes, severity, timeout bounds and regular-expression syntax before any SUT call. The initial 15 templates expand to 16 concrete instances.

## Coverage boundary

The 15 templates expand to 16 concrete cases. Static validation does not claim that every rule passes against a real SUT. The PR workflow runs them against `scripts/ci_mock_sut.py`, which deterministically exercises Gate's ChatKit transport, trace normalization, evaluators and reporting without an external model. This is a Gate pipeline contract fixture, not evidence about live agent quality. The manual live smoke runs AIR-01 against the locked SUT and configured model. P5's runner creates a fresh thread per case and runs serially; real model output can still vary.

The [sample JSON/Markdown report](examples/sample-airline-status-20261108/sample-run.md) is generated by applying AIR-01 to the previously captured sanitized real-SUT trace; it documents one observed passing run.
